### Kept in child themes — justified

The remaining 627 selector overrides fall into categories that are
**not** technical debt — they encode genuine theme behavior that
doesn't generalize to a clean token, or that lives in admin-only
widgets whose surface area is too narrow to deserve dedicated tokens.

**Bucket A residual (62)** — color-only overrides whose color values
don't map cleanly onto any of the 33 tokens (e.g., one-off accent
shades for `.AddIconTitle`, `.UsernameBlock.success_message`,
`.activity-filter-container`).

**Bucket B residual (49)** — rules duplicated across both children
but missing from base. About half target `???` (no obvious base-file
home — would require new files like `components/jconfirm.css`,
`components/token-input.css`, `pages/comments-filters.css`). The
remaining bucket-B rules are mostly asymmetric in property sets
between dark and light (e.g., `.bigbutton/.bigtext` family — light
uses no-sprite layout, dark uses sprite-based imagery; reclassified
as effectively X-equivalent).

**Bucket C residual (275)** — dark overrides of base rules where:
1. The override value is a one-off color with no cluster pattern
   (e.g., `.cache-size-value`, `.princes-of-this-piwigo`).
2. The semantic role of the override is asymmetric with light's
   (e.g., `.intro-charts .tooltip` `box-shadow:none` only in dark).
3. The color comes from a third-party widget's internal palette
   (jconfirm, token-input, datepicker chrome) that has its own
   theming model.

**Bucket E residual (139)** — dark-exclusive rules covering
third-party-widget overrides whose CSS surface is integrated into
the theme files (jconfirm, token-input, pluginTypeFilter). These
have their own internal theming structure and migrating them would
require creating component-CSS files outside the existing base/
shape.

**Bucket F residual (29)** — light-exclusive structural rules
(`#copyright`, `#footer`, `input[type="file"]`, `*:focus`, etc.).
Some are genuinely light-only (footer link styling for light);
others are misplaced but the migration would require creating new
base files for narrow utility selectors.

**Bucket X residual (42)** — asymmetric property sets between dark
and light. Each rule legitimately sets a different property in one
theme vs. the other (e.g., dark sets `border-color`, light sets
`background-color` for the same element). These are by definition
not tokenizable — they represent genuine theme-specific structural
choices.

**Bucket D (31)** — light overrides of base rules. Small enough to
leave as-is; tokenizing would require introducing many narrow
single-use tokens.

### Visual smoke test required

Per the §3.1 plan, an end-to-end visual smoke is needed across:
- dashboard
- batch_manager unit + global
- user_list
- picture_modify
- configuration_main
- cat_modify
- plugins
- comments
- intro

In both dark and light themes. Several batch commits documented
intentional minor visual normalizations (popin titles emphasized in
dark, cancel-text brighter in dark, badge-dropdown gradient → flat,
plugin-version brighter in dark, chart tooltip-title brighter in
dark, options[disabled] muted in light). These should be
confirmed visually before final sign-off.
