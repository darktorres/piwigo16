A complete rewrite log

Piwigo in Modern PHP

Photo gallery software doesn't get less popular as it gets older, and Piwigo turned twenty-three this year — old enough that most of its code predates PHP having namespaces. This is the complete account: everything that was wrong with it, and all fifty-five phases it took to fix.

TL;DR

Piwigo is a 23-year-old PHP photo gallery that, until this rewrite, had no automated test suite — the one file with "test" in its name was a manual, framework-free bootstrap script — plus zero Composer, every table on MyISAM, and a home-rolled 94-method RPC API that turned out to have real, live security bugs — I found and fixed seven of them in one week, including a session-privilege-escalation bug and an authenticated arbitrary-file-write. The rewrite replaces all of it: PSR-4 plus dependency injection plus Doctrine ORM, a six-layer architecture Deptrac enforces at zero violations, PHPStan at its strictest level with zero errors, a real REST API (/api/v1, OpenAPI, tus uploads) replacing the legacy RPC layer, Smarty swapped for Latte with one typed view object per template, jQuery and every IE-era shim gone, a real plugin/theme contract with dependency resolution so a core upgrade stops being a coin flip for every installed extension, and translations moved to real .po files a tool like Weblate can actually read. Fifty-five phases, 4,579 commits, about sixteen weeks, 9,246 real tests replacing that one manual script.

Part one

Where we started

Eleven problems, each a direct symptom of the same twenty-three-year-old shape of codebase — not independently fixable bugs, which is the whole case for a rewrite rather than a cleanup pass.

01

No packaging, no PSR, not even a place to start

Piwigo's first commit is dated May 9, 2003. Whatever you're picturing when I say "twenty-three-year-old PHP," picture something with no composer.json in it at all — not deprecated, not half-migrated, absent, because there was never a package manager to omit it from. I checked the pristine tree directly before writing this:

  • Zero composer.json, anywhere in the tree — every dependency is either vendored by hand or not managed at all.
  • Zero namespaces, zero PSR-anything — one flat procedural include graph.
  • A declared floor of PHP 7.4 — not literally PHP 5, whatever it might look like — but eleven call sites still reach for functions PHP removed outright in version 7.0.
  • No static analysis, because there's no type system disciplined enough to analyze; no CI, because there's no test suite for a pipeline to run.
install/piwigo_structure-mysql.sql · admin/include/pclzip.lib.php
// ereg() is deprecated with PHP 5.3
if (ereg($p_options[PCLZIP_OPT_BY_EREG], $v_header['stored_filename'])) {

That comment is original to the file — someone already knew, in the PHP 5.3 era, that this call site was on borrowed time. It's still there. This isn't a codebase that skipped a few modern conveniences. It's a codebase from before most of them existed, that never got a second pass.

02

State lived in whatever global was closest

Every request built its working state out of five superglobal-adjacent variables any of a few hundred files could read and mutate, in any order, with no compiler or type checker able to say who owned what:

include/functions.inc.php:426
global $conf, $user, $page;

Underneath that sat a roughly 230-call-site service locator, the same shape you'd get from a container if a container ever bothered to enforce what it handed out. None of it was hidden or embarrassing by the standards of when it was written — PHP in 2003 didn't have autoloading, so a global was often the honest, idiomatic answer. The problem is what happens when the honest 2003 answer is still the load-bearing one twenty years later.

03

Singletons pretending to be services

Layered on top of the globals was a second flavor of shared state: static classes and service-locator singletons holding process-persistent data with no way to reset between requests short of restarting PHP. Under classic per-request execution that's merely ugly — the process dies at the end of the request and takes its accumulated state with it. It stops being merely ugly the moment you want a process to survive across requests, which turns out to matter a great deal later in this piece.

04

MyISAM tables under a photo gallery

The data layer was hand-built SQL string concatenation, glued together by a Tables:: helper whose entire job was returning a table name as a string — opaque enough to defeat any static SQL tool that wants to see a literal string, which is exactly what it was handed instead. There was no ORM and no schema-migration mechanism; the schema was whatever the install script last wrote and whatever ad hoc ALTER TABLE a version bump remembered to run.

The detail that actually surprised me: every one of the 34 tables in the pristine install schema is declared ENGINE=MyISAM. Not a mixed bag, not "most tables" — all of them, on an application whose entire job is concurrent writes racing concurrent reads: uploads, comments, ratings, tag assignments, session rows, all fighting for the same table-level lock MyISAM hands out, with no transactions and no foreign keys to catch a half-finished write.

install/piwigo_structure-mysql.sql
CREATE TABLE `piwigo_categories` (
  `id` smallint(5) unsigned NOT NULL auto_increment,
  `name` varchar(255) NOT NULL default '',
  […]
) ENGINE=MyISAM;

That's not a nitpick you'd only notice under heavy load. It's a structural ceiling on how much traffic the thing could ever safely serve.

05

One template, one untyped bag of everything

Templating ran on Smarty, and the working contract between a controller and its template was "whatever got assigned to the one shared variable bag, under whatever string key the controller author chose that day." Nothing checked that a template's expectations matched what a controller actually sent it — a typo in a variable name failed silently, rendering an empty string instead of an error. Nothing stopped a template from reaching back into a controller's internals, or a controller from reaching forward into template state. The boundary existed only as a convention two different people had to remember to respect.

06

Ninety-four ways to reach into the same god-class

Every mobile app, every third-party client, and a good chunk of the site's own UI talked to Piwigo through a single hand-rolled JSON/XML RPC layer — 94 methods deep. They didn't look like 94 independent, well-scoped endpoints:

  • All 94 were entries in one shared registration array, dispatched by a single method whose entire job — registering the other 94 — ran to 1,322 lines by itself.
  • Parameters arrived as array $params, read back out by string key, with no type anywhere between "whatever the client sent" and "whatever the handler assumed."
  • Errors and early exits didn't return — they called exit() straight from deep inside business logic, a fine way to end a script and a terrible way to compose one.
07

What a week of careful reading turned up

I went into the WS layer expecting to modernize its internals without changing a single byte on the wire. Somewhere in the middle of reading it carefully, the read turned into a security review, and the security review turned up seven real, exploitable findings. All seven were fixed the same day they were found:

  1. Every superglobal, on every single request, ran through a blanket addslashes() call — silent data corruption on anything containing a backslash or quote, server-wide, on every request the app served.

  2. An upload endpoint used a session type meant to stay maximally restricted — an API-key session, scoped to a small handful of calls. A bootstrap ordering bug let it silently upgrade itself into a fully authenticated session, unlocking eight endpoints that were supposed to be permanently unreachable from it.

  3. One upload endpoint wrote a file to disk using a checksum and MIME type read straight off the request, unvalidated — an authenticated user could write to a directory of their choosing.

  4. One admin action was missing an authorization gate that its nearly identical sibling action already had.

  5. CSRF protection on three state-changing endpoints was optional, because the same token field doubled as an unrelated "allow raw HTML" flag — and one of the three was reachable over a plain GET.

  6. CSRF tokens were compared with !== instead of a constant-time comparison — a timing side-channel on the one check standing between a real form submission and a forged one.

  7. Four separate exec() call sites passed their arguments straight through with no escaping at all.

None of these seven tripped a single existing test. The suite covering that API — six hundred and four tests deep, covering all ninety-four methods — was there to check that the wire format hadn't changed. It was never asked whether the wire format was safe, so it never had a chance to say no.

You can fix seven bugs like that in an afternoon, and I did. What you can't do is code-review your way out of the thing that produced them: an architecture where safety is something each of ninety-four independent handlers has to remember to do for itself, in a codebase where state lives in whichever superglobal or static class property happened to be closest at the time. Blanket addslashes() on every request wasn't a one-off mistake — it's what happens when there's no single, typed choke point request data is forced through.

08

A plugin ecosystem playing roulette with every release

Roughly four hundred real plugins exist for Piwigo, plus a long tail of themes, and every one of them was written against undocumented internals rather than a contract:

  • No real contract — only header-comment marker files (main.inc.php, themeconf.inc.php) declaring a name and a version string nobody actually enforced.
  • No dependency resolution between plugins.
  • No real negotiation between a plugin's declared compatibility and core's actual version.

The practical result, if you've run a Piwigo install with more than a couple of plugins through more than one upgrade: every core release is a coin flip for every installed extension, because plugins reach directly into whatever internal shape core happened to have that particular week. Nothing stood between them.

09

jQuery, IE7 shims, and a home-rolled bundler

The frontend was jQuery-dependent front to back, and everything downstream of that one dependency stayed frozen at roughly the same era:

  • IE6/7 conditional comments and fallback stylesheets, still live in the tree.
  • No TypeScript, no modern CSS architecture, no CSS containment or cascade layers — none of that existed yet when most of the stylesheet was written, and nobody had been back to use it since.
  • No build tool in the sense anyone shipping a frontend in 2026 would recognize one — instead, a roughly thousand-line hand-rolled PHP class walked templates at request time looking for script and style declarations to concatenate and minify itself.
  • No dark mode. No responsive image pipeline.
10

Translations only a PHP developer could touch

I checked this one directly too: the pristine tree has zero .po or .mo files anywhere. Every locale — sixty-plus of them — is a .lang.php file, a bespoke PHP array (admin.lang.php, common.lang.php, one file per locale per page-group) that no translation platform on earth speaks. Weblate, Crowdin, POEditor — they all work in gettext/PO, and none of them work in "PHP array a Piwigo maintainer hand-edited in a text editor." Translating a string meant being comfortable opening a PHP file and not breaking its syntax. That's a strange bar to clear for a job that has nothing to do with programming.

11

No quality gates worth the name

Last, and in a sense the root cause behind letting all the rest persist this long: I checked, and the pristine tree has —

  • No tests/ directory, and no automated test suite worth the name.
  • No CI.
  • No mutation testing.
  • No accessibility or performance budget.

There's exactly one file in the whole tree with "test" in its name — tools/test_piwigo.php — and it's worth being precise about rather than waving away: 339 lines, no framework, no real assertions. It installs a fresh Piwigo, logs in, creates an album, then shells out to a separate Perl script to upload a photo and prints "Add a Picture OK!" or "...KO!" to the terminal based on a raw row count — no pass/fail exit code, nothing a pipeline could act on, and its own picture-upload verification branch is half commented-out dead code. It's a manual bootstrap script a developer runs by hand and reads with their own eyes, not a test suite. Nothing in this tree — that file included — would have caught any of the eleven findings above automatically, because nothing was actually looking. A codebase can drift a long way in twenty-three years when nothing pushes back.

None of these eleven things are independently fixable bugs. They're symptoms of one shape of codebase — one where nothing enforces a boundary, nothing types a contract, and nothing runs on every change to notice when a boundary gets crossed anyway. You can patch a `addslashes()` call. You cannot patch your way out of an architecture that made blanket `addslashes()` the path of least resistance in the first place. That's the case for a rewrite, not a cleanup pass — and what follows is all fifty-five phases of it.

12

The rewrite, in ten epochs

Fifty-five phases, P0 through P54, sequenced so every backend phase lands before any frontend phase touches it. None of it got copy-pasted forward — the rule for the whole effort was read the target behavior, then reimplement it by hand, tests first or in the same commit, full gate suite green before the next commit group started. What follows is all of it, epoch by epoch.

A

Foundation

P0 – P4

Five phases, and not one line of first-party application behavior changes in any of them. Epoch A's entire job is standing up the tools, harnesses and infrastructure everything after it gets held to — additive only, on purpose, so that when P5 makes its first real code-modifying pass, there's already a baseline to measure drift against instead of a guess.

P0Every checker, installed before a single line changes

Problem

Section 01 already made the case in the abstract: no static analysis, no test framework worth the name, no dependency-hygiene tooling, nothing gating a CVE from entering the tree. Concretely, at the moment this phase starts, there is no way to answer the question "did the last change make this codebase better or worse" with anything other than a guess.

Plan

Install every tool the rest of the project will eventually be held to, but run all of them in measurement-only mode first, before any code-modifying pass touches the tree — so the first real refactor (P5) and the tooling adoption itself never get tangled into one diff nobody can bisect. And pick the strictest PHPStan level immediately rather than ramp up incrementally: ratcheting a level up later means re-auditing everything that already passed at a lower one, which is strictly more work than starting at the ceiling.

Fix

Pest as the sole test framework, pulled in with its architecture, browser, mutation-testing, PHPStan-bridge and type-coverage plugins so one runner covers five different kinds of test from day one instead of stitching PHPUnit, Behat and a separate mutation tool together by hand. Easy Coding Standard for style — ECS is itself a thin orchestrator over two different underlying engines, not one: PHP-CS-Fixer for the formatting rules (spacing, import order, declare(strict_types=1) placement) and, layered on top of that, a raw PHP_CodeSniffer sniff for the one thing PHP-CS-Fixer's rule set structurally can't do — renaming. PSR-1's camelCase method-name requirement needs an identifier-aware sniff, not a formatter, and it runs report-only by design: auto-renaming a method could silently break an interface implementation or a plugin override, so a human has to make that call, the tool only has to flag it.

PHPStan runs at level: 10 — the strictest rung the tool offers — with vendor/phpstan/phpstan/conf/bleedingEdge.neon included on top, which pulls in rule tightenings the PHPStan project itself considers correct but hasn't stabilized into a numbered level yet. Layered onto that: extensions for Doctrine, PHPUnit, Symfony and a general strict-rules pack, plus staabm/phpstan-dba, a SQL-string analyzer that validates query text against the real schema — but only works against literal strings, since it has to parse the SQL statically. That one constraint turns out to matter a great deal later: it becomes part of the actual case, several epochs on, for deleting a table-name helper whose entire job was building query fragments as opaque, non-literal strings — the helper wasn't just an abstraction nobody liked, it was invisible to this analyzer by construction.

Rounding out the PHP side: Rector for mechanical modernization (its actual PHP 8.5 rule set doesn't get turned loose tree-wide until P5 — this phase only installs it); Deptrac for the architecture-boundary checker, with its real six-layer ruleset still three phases away in P6; Psalm as a second, deliberately non-blocking opinion, since two gates that can both flag the same line teach people to distrust whichever one cries wolf more; ComposerRequireChecker and ComposerUnused for dependency hygiene; PHPBench for microbenchmarks; pcov as the code-coverage driver rather than Xdebug, chosen specifically because it's faster for coverage collection and nothing here needs Xdebug's step debugger in CI; and roave/security-advisories, pinned to dev-latest, which does something quietly aggressive by design — it's a metapackage with deliberately conflicting version constraints against every package with a known CVE, so composer install fails outright the moment a vulnerable version enters the dependency tree, rather than waiting for a nightly scanner to notice after the fact.

Friction
phpstan.neon
# Defaults to the machine-wide sys_get_temp_dir()/phpstan, shared by
# every worktree on this box -- the dead-code-detector extension's own
# UsageCacheStorage keys its cache purely by content hash and garbage-
# collects entries its own process didn't read, so two worktrees
# analysing overlapping content concurrently race on the same cache
# files ("DCD cache file not found for hash ..." is the symptom).
tmpDir: /tmp/phpstan%currentWorkingDirectory%

PHPStan's own dead-code-detector extension caches analysis results keyed by content hash in a shared temp directory, and two people — or two worktrees on the same machine — running an analysis at the same time race on the same cache files, one process garbage-collecting entries the other hasn't read yet. Not a hypothetical: the symptom string in that comment is a real error a real run produced. The fix folds the current working directory into the cache path itself, giving every worktree its own real, collision-free location — the kind of operational scar tissue that only shows up once real people are running the tool concurrently, which is the entire point of turning it on this early rather than after the first real refactor is already in flight.

Verification

The measurement-only sequencing is verified less by a single check than by what didn't have to happen afterward: every tool named above is still, identity for identity, what's running today — nothing needed to be swapped out once real usage started. P5's later switch from report-only to code-modifying never had to re-litigate which tools to trust; it only had to flip a mode.

Result

Every phase after this one has somewhere to stand. P5's tree-wide Rector and ECS pass has a baseline to diff against instead of a guess, and because the strictest PHPStan level was the starting point rather than a later goal, no phase downstream of this one ever had to stop and re-audit code that had already passed a lower bar.

P1Bun, Vite, and a real frontend quality bar

Problem

Section 09's indictment, restated concretely for this phase: no bundler, no linter, no perf budget, nothing standing between a change and the page it ships to. A jQuery-era frontend with no tooling has no way to notice its own regressions either.

Plan

Mirror P0's additive-first approach on the frontend — install the full modern toolchain before any frontend code gets touched, so the eventual TypeScript/CSS modernization work several epochs later inherits gates that already exist rather than having to build them mid-migration.

Fix

bun as the package manager and script runner, Vite as the bundler, TypeScript, ESLint on a flat config with typescript-eslint, Stylelint, Vitest with real v8 coverage, knip for dead-export and dead-dependency detection, size-limit for bundle budgets, commitlint enforcing the conventional-commit convention this project's own git history depends on to stay legible, and Lighthouse CI for performance and accessibility scoring — collect-only at this phase, reporting real numbers into .lighthouseci/ with nothing yet enforced against them; turning those numbers into a real blocking threshold is P54's job, once there's a finished frontend worth holding to one.

knip's configuration is worth a look on its own, because it's a small, concrete example of a tool needing real domain knowledge to not lie: its entry-point list has to explicitly exclude the vendored jQuery bundle, jQuery's cookie plugin, and the IE-era PNG-alpha shim from dead-code analysis — not because they're used in a way knip can't see, but because they're third-party files this project doesn't touch and doesn't want flagged as unused exports of its own code. Get that exclusion list wrong and a legitimate finding tool starts crying wolf about files nobody was ever going to act on, which is the fastest way to get a whole category of tooling ignored.

Friction
vite.config.ts
// Vite's own default publicDir ("<root>/public") collides with this
// project's public/ -- the PHP app's web root -- not a "static assets to
// copy into the build output" directory in Vite's sense. Left at the
// default, the build's own publicDir-copy step walks into public/dist (a
// symlink back to this very outDir) and recursively copies dist/ into
// itself without bound -- real bug: a `vite build` run filled the disk
// (dist/dist/dist/... nested ~100 levels deep, ENOSPC) before this was set.
publicDir: false,

Not a hypothetical risk written up defensively after the fact — a real incident, caught during setup: a routine build run silently recursed into its own output directory through a symlink loop and kept copying until the disk filled up. The fix is one line, because nothing here actually needed Vite's copy step in the first place — the build's own outDir already is what public/dist symlinks to, so the built assets are reachable at /dist/... with zero copying required.

A second, quieter gap sat unnoticed for longer: web-vitals got installed on day one but was never wired to anywhere real field metrics could go — a library in package.json measuring nothing, until someone noticed.

Verification

The web-vitals gap is closed by a small build/vitals.ts collector calling navigator.sendBeacon() against a real VitalsController and route, loaded on every page — log-only, no dashboard, but a real endpoint now receiving real Core Web Vitals numbers from real page loads. The proof it works is the plainest kind: the endpoint has traffic.

Result

The frontend modernization epoch, several dozen phases away, inherits a proven toolchain instead of standing one up mid-migration — and a Lighthouse baseline is already being collected years before P54 turns it into a real blocking gate.

P2An environment split, a fixture database, and suites that didn't exist yet

Problem

Section 11's indictment: no automated test suite anywhere — the one file with "test" in its name is a manual, framework-free bootstrap script, not something a pipeline could run. Even once P0 installs Pest, there's nowhere disposable to run it against and no way to guarantee two runs start from the same state.

Plan

Build the harness before any domain code migrates — env split, fixture database, five real test suites — so every phase from here forward has somewhere to write a test on day one, rather than inventing test infrastructure ad hoc, differently, each time a new phase needs it.

Fix

A dedicated test mode — a separate .env.test file plus an X-Piwigo-Env: test header the app checks on every request through one small Env class — so the exact same code path that serves production can run against a disposable fixture database in CI without a single if (testing) branch anywhere in application code. The same env file pins a frozen test clock, so nothing built against "today" flakes on whatever day CI happens to run, and points a trio of alternate PEM-mirror URLs at local fixtures instead of the real network, so the plugin/theme catalog work several epochs later has something deterministic to test against from day one.

The fixture itself is a real, reimportable SQL dump — tests/Fixtures/piwigo-17.0.sql, 39 real tables, with a Postgres variant sitting alongside it well before the multi-provider work that would come to depend on it — so every test run starts from a known, identical state rather than whatever the last run happened to leave behind. Five real test suites get their directories here: Unit, Arch, Integration, Contract and Browser, each wired into its own phpunit.xml.dist testsuite entry so any of them can run in isolation. A WS Contract suite gets one dedicated file per RPC method family from the start — WsCategoriesTest, WsCommentsTest, WsGroupsTest, WsApiKeyTest and dozens more, 42 files in total.

Verification

Neither Browser nor Contract has much real coverage yet at this phase — they exist here so later phases have something to run against, not because P2 itself proves much. The real verification of this phase's value doesn't land for several epochs: it's the WS Contract suite staying completely unmodified all the way through P25's ninety-four-handler RPC modernization. A suite built now, untouched then, is the whole proof that migration changed nothing on the wire.

Result

Every phase after this one gets to write tests immediately instead of asking "against what." The frozen clock and fixture PEM URLs mean determinism was a day-one property, not something bolted on once flaky tests started showing up.

P3Thirty-four jobs, and the rule that all of them have to pass

Problem

P0 through P2 install real tools and build a real harness, but a tool that only runs when someone remembers to run it locally isn't a gate — it's a suggestion. Nothing yet forces any of it to run on every single change.

Plan

Wire every already-installed tool into a real pipeline immediately, sequenced right after the harness so CI has real suites to run rather than empty placeholders — and treat supply-chain scanning as day-one scope alongside it, not a hardening pass added after an incident.

Fix

The pipeline this whole project runs on, clustered by what each group actually checks rather than just named: pest (composer test) and a separate coverage job running the same suite again under pcov; ecs/phpstan/rector/deptrac for static analysis, each invoking the real composer script rather than a bare binary call so local and CI runs can never quietly drift apart; audit (composer audit --abandoned=report, flagging both known vulnerabilities and dependencies their own maintainers have marked abandoned); require-checker, composer-unused and composer-normalize for dependency hygiene; phpbench; a matching frontend cluster — vitest, eslint, stylelint, knip, prettier, markdownlint; size-limit, which runs a real production build first so the budget check measures the real shipped bundle, not an estimate; commitlint, run three different ways depending on whether the trigger is a pull request, a push, or a single commit; actionlint, linting the CI configuration's own YAML; a doc-drift job re-executing every machine-checkable claim embedded in docs/PLAN.md; a db-multi-provider matrix plus dedicated integration, contract, browser, install-flow and visual-regression jobs, the last four driven by a real headless Chromium through Playwright; a restore-drill job; lighthouse; an sbom job; and apache-deny-rules/container-deny-rules, which don't just lint the deny-rule configuration — container-deny-rules builds the real production image, boots it, and curls the denied paths against a live running container. Thirty-four jobs today.

The sbom job generates two separate software bills of materials — one for the PHP tree via composer sbom, one for npm via a locked-down cyclonedx-npm invocation — then runs actions/attest-build-provenance against them, a real, cryptographically signed provenance attestation tying the artifact back to the exact workflow run that produced it. Every third-party GitHub Action across the pipeline is pinned to a full commit SHA rather than a mutable tag, so a compromised or re-tagged upstream action can't silently swap in different code under a name CI already trusts. OSV vulnerability scanning and an OpenSSF Scorecard check both run as their own scheduled workflows, every Saturday at 1:30am, independent of any commit — so a new CVE published against an already-merged, otherwise-unchanged dependency still gets caught within the week.

Verification

The pipeline verifies itself by construction: nothing lands unless CI is green on a clean checkout. Not a local machine, not "it passed on my branch" — the clean-checkout run in CI is the only claim of "passing" this project recognizes.

Result

Every phase from here forward is held to the exact same gate, automatically, with no opt-out. A regression or a security finding closed once can't silently reopen later without CI noticing on the very next push.

P4Three server targets, one set of rules

Problem

Nothing yet says how this actually runs anywhere real. No reproducible build, no documented deploy path, no verified way to recover from a bad restore — "it works on the machine that built it" isn't a runtime story.

Plan

Build real, independently buildable server targets rather than one image behind a flag, so the primary FrankenPHP runtime and an Apache fallback are both genuinely production-shaped, not one blessed path and an afterthought. Mirror security policy across every target deliberately rather than trust one canonical source to stay in sync by memory. And prove restore capability with an actual rehearsed drill, not a documented hope.

Fix

Six real, independently buildable Dockerfile stages. A Composer builder resolves PHP dependencies with --ignore-platform-reqs, since the bare composer:2 image isn't the target runtime. A bun-based frontend builder runs the real production build. The production stage runs on dunglas/frankenphp:1-php8.5 — the primary runtime this whole project is aimed at — installing only the five PHP extensions the base image doesn't already ship (verified directly against php -m), then deliberately skipping --auto-remove when purging the -dev/headers packages those extensions needed to compile, since auto-removing would cascade into deleting the runtime shared libraries — libpng16, libicuio, libMagickWand — those same packages pulled in and the compiled extensions still need loaded at runtime. A dev variant layers Composer and bun back onto the production image for a single container with both toolchains available. A frontend-only test stage runs Vitest in isolation. And a separate php:8.5-apache fallback shares the same extension list, with its own vhost pointed at public/ instead of the whole source tree.

Six Dockerfile stages — arrows show COPY --from / FROM relationships

The production container listens on port 80 as the non-root www-data user, needing exactly one Linux capability — CAP_NET_BIND_SERVICE — to bind a privileged port without being root. Verified empirically: FrankenPHP wants that capability at startup regardless of which port it ends up binding, so a high port bought nothing. Compose and Helm both grant it the same narrow way — cap_drop: [ALL] then cap_add: [NET_BIND_SERVICE], one specific exception carved back out of nothing, not Docker's ~14-capability default and not root. The web-root deny policy (SEC-01) is written once in intent and mirrored across all three real targets — Apache's .htaccess, the Caddyfile, and the CI job that checks the container at runtime — because a rule that exists in one config and not its siblings is a rule an attacker only has to find the gap in.

Friction

That mirroring is what caught a real bug during the P4 audit, not a hypothetical one: the Apache rule denying access to vendor/ was written as an unanchored pattern matching /vendor/ anywhere in the request path, which also matched and 403'd every icon glyph under themes/default/vendor/fontello/ — a real, legitimate, publicly-servable bundled font, sitewide, the moment AllowOverride All made the rule active. Found via a real curl returning 403 and a matching Apache access-log entry, root-caused rather than written off as a browser timing flake, and fixed by excluding any vendor/ nested under themes/*/ or plugins/*/.

# isn't a real static file under /app/public silently falls through to
# index.php instead of 404ing at the web-server layer.
@deniedRelocated path /upload/* /galleries/* /local/* /language/* /plugins/*
respond @deniedRelocated 403

A second finding on the Caddy side, distinct from the Apache one: moving the document root to public/ made most of the source tree structurally unreachable by construction, but a handful of directories the app still needs at runtime — uploads, gallery storage, local overrides — live outside public/ too, and Caddy's own catch-all fallback quietly routes anything that isn't a static file straight to index.php rather than 404ing. "The document root doesn't cover it" and "it's unreachable" turned out to be two different claims, and the gap between them needed its own explicit deny rule. Caddy's path matcher, checked directly rather than assumed safe by similarity, turned out not to share the Apache anchoring bug at all — it anchors each pattern to the start of the URI, so /vendor/* there only ever matches the real top-level Composer directory.

Verification

container-deny-rules doesn't just lint the configuration — it builds the real production image, boots it, and curls the denied paths against a live running container to prove the rule holds at runtime, not just on paper. And the restore drill actually restores the tracked fixture dump into a scratch database and asserts real row counts and a schema smoke query against it — kept deliberately independent of the project's own backup-restore CLI command, so the mechanism proving disaster recovery works isn't allowed to depend on the same application stack it exists to rehearse recovering.

Result

Three real, working server targets instead of one blessed path. SEC-01 proven to hold identically across all of them, not assumed to. Two narrower rules round out the posture: SEC-06 marks every content-hashed Vite asset immutable for a year, since a hash change is the only way its content ever changes; SEC-21 forces any uploaded .svg/.html file to download rather than render inline, defense in depth alongside the real fix that strips <script> tags and event handlers out of uploaded SVGs at upload time. And /health//ready stay deliberately outside the normal request pipeline on both server configs, so the one part of the app that's supposed to answer honestly when everything else is on fire doesn't depend on any of the things that might be on fire.

B

Composer, Rector, PHPStan & PSR-4

P5 – P6

P5The single largest phase by commit volume: a whole-tree style pass, PHPStan's bleeding-edge ruleset applied file by file across what was still a non-namespaced procedural tree, and every vendored or ad hoc third-party dependency replaced with a real, native-platform-first equivalent — Symfony Mailer over a bundled mailer library, a real QR-code and HTML-inlining package, `password_hash()` over a hand-rolled hashing shim. Rector's full PHP 8.5 and type-declaration rule sets run tree-wide. Property hooks and asymmetric visibility land on the config object specifically, cutting it by more than half while removing real boilerplate, not just reformatting it.

P6Every first-party class gets physically extracted out of the procedural `include/`/`admin/` files it used to live inside, into a real PSR-4 tree under one namespace root. This is extraction and namespacing only — no renaming, no DI, no behavior change beyond what the move itself forces — but it's the phase that makes everything after it possible, and it's where the six-layer Deptrac architecture model gets established for the first time.

C

Kernel & HTTP foundation

P7 – P12

P7A real kernel and boot skeleton — and the payoff the rest of this piece keeps pointing toward: FrankenPHP running in genuine worker mode, the app process staying booted in memory and handling a long run of requests back to back instead of booting fresh for every single one. Every static-singleton removal described later in this piece exists to make this safe.

P8A real dependency-injection container, autowired by default — a constructor with only class-typed parameters needs zero explicit container configuration.

P9A full PSR-15 middleware pipeline and routing layer, replacing the ad hoc bootstrap-then-run sequence every request used to be walked through by hand — plus a real CSRF and security-header hardening pass, fixing timing-unsafe comparisons that had sat unnoticed for years.

P10Structured logging, request timing headers, and distributed tracing — observability that answers "what actually happened on this request" instead of forcing someone to grep a flat log file.

P11A real cache layer with named pools tuned per use case — config, permissions, category tree, tag cloud, rate limiter, general — plus a real async job queue with actual admin-visible failure handling, not a queue whose failures vanish silently.

P12A proper CLI tool, real backup and restore commands, graceful shutdown on SIGTERM so an interrupted backup doesn't leave temp files scattered around, and a full set of maintenance commands for the janitorial work every long-running gallery eventually needs — orphaned tags, stale history, expired sessions, table repair.

D

Config, DB & language

P13 – P16

P13A typed configuration service — 277 real settings, each with a real type instead of "whatever was in the database row" — with its required-value and sensitive-value markers actually wired into boot and the error handler, not left as decoration.

P14Doctrine ORM replaces hand-rolled, string-built SQL across the board: 38 domain repositories, each either a real entity repository or, where the access pattern was genuinely too dynamic for a mapping to fit honestly, built directly on the entity manager instead of pretending otherwise.

P15The schema itself: InnoDB and utf8mb4 uniformly across every table — the direct fix for the MyISAM problem from section 04 — real foreign-key constraints, and a genuine audit log.

P16Typed facades for paths, the current user and page state replace scattered constant lookups; the translation migration described in section 10 lands here for real — the `.lang.php` files are gone, replaced by real `.po` files and ICU MessageFormat pluralization.

E

Service layer

P17 – P23

P17–P20Roughly 35 domain namespaces migrate out of the legacy tree in four dependency-ordered tiers, each tier depending only on the ones already landed: URL, session, HTML and CSRF handling first; mail, users, auth, tags and comments next; category, image, search and calendar after that; page renderers, menus and jobs last. Each tier's legacy file is deleted the moment its replacement lands — nothing gets batched to the end and left to rot in parallel with its own replacement.

P21Every admin page becomes a real, decomposed sub-controller — 37 of them — with no god-class dispatcher reproducing the old monoliths under a new name.

P2219 real frontend controllers. Install correctly stays a special unrouted entry point rather than becoming a controller (it has to work before any database or config exists), and there's no upgrade controller at all — a clean fork doesn't need one.

P23The big one: `include/` and `admin/` are deleted as directories, outright. Every `global` statement is gone, every bridge free-function is gone, and the legacy hand-rolled data-access layer is gone with them. This is the phase where the old codebase actually stops existing underneath the new one, rather than lingering as a shadow the new code quietly still depends on.

F

Post-migration remediation

P24

One phase, but the hardening pass after the big structural move, covering several tracks worth naming individually.

P24The last hand-rolled data-access code gets migrated onto real Doctrine repositories project-wide. Every remaining `$GLOBALS` and static-bridge reference — `$template`, `$lang`, `$user`, `$conf`, `$page`, and roughly 25 smaller globals — gets retired for good. The event-dispatch and localization free-function bridges get retargeted onto real classes. Every remaining untyped `Template::assign()` call becomes one of 130 typed template-context classes. Roughly eighty controller actions get a typed request object of their own, replacing raw `$_POST`/`$_GET` reads, guarded going forward by a standing architectural test. And the table-prefix mechanism — a holdover from an era of shared hosting where one database served several installs — gets deleted outright rather than merely made optional, inlining well over a thousand call sites from a verified mapping.

P24Killing the singletons

The one piece of this epoch worth its own paragraph. About fifty-five classes across three different static-singleton and service-locator shapes get converted to constructor-injected dependency injection over seventy-four commits — including the WS layer's entire static-dispatch mechanism as its own sub-phase. The mechanism was deliberately conservative: each class got a transitional, explicitly deprecated static shim for callers not yet converted, tracked by a shrinking architectural-test allow-list, with a hard rule that the campaign isn't done until that list hits zero. It hit zero, and stayed there.

This was never a style argument. It's the precondition for P7's worker mode actually being safe: process-persistent static state is not a performance nitpick under a model where the app process survives across many requests — it's a correctness bug waiting to happen, one request's leftover state quietly becoming the next, unrelated request's starting condition. Fixing that after the fact, one class at a time, forever, would have cost more than removing the pattern outright, once.

G

WS layer & REST

P25 – P27

The centerpiece migration, and the one that produced section 07's bug catalog along the way.

P25The RPC layer, twice

The ninety-four-method WS API didn't get replaced in one step — it got modernized in place first, then replaced. Stage one kept the wire format byte-for-byte identical (the unmodified 604-test Contract suite from P2 was the proof) while gutting everything behind it: the 1,322-line registration method split into thirteen per-domain registrars, ninety-four hand-written callback registrations became ninety-four constructor-injected handler classes, and seventy-eight typed parameter objects replaced array $params read by string key. This is also the pass that surfaced and fixed the seven security findings in section 07, the same day they were found.

P26Moving the UI off its own back channel

Roughly fifteen WS methods existed purely to feed the site's own admin UI over the same JSON/XML envelope external clients used. Those move onto server-rendered fragments instead — the UI stops round-tripping through its own public API just to update part of a page.

P27A real public API

Only once every handler had a real type signature instead of a string-keyed bag of whatever the client happened to send did the actual replacement begin: a REST surface at /api/v1, described by a real OpenAPI 3.1 specification, backed by a generated and typed TypeScript client, with the old nine-step chunked-upload dance replaced by the real tus resumable-upload protocol. The legacy layer — every handler, every encoder, the envelope format itself — comes out in the same phase its replacement covers it. Not before.

P27A plugin ecosystem that stops playing roulette

This is the direct answer to section 08's problem. ExtensionInterface replaces undocumented internal reaching with one shared, documented contract for both plugins and themes. Manifest files (plugin.json/theme.json) replace the old header-comment markers entirely, and — the actually new capability — a manifest can now declare a real version constraint against core and against other plugins it depends on, resolved into a real dependency graph. Activating a plugin whose requirement isn't met now fails cleanly instead of installing something broken; deactivating a plugin another active plugin still depends on refuses instead of silently breaking the dependent. It's the same category of guarantee a package manager gives an ordinary dependency tree, applied to Piwigo's own extension ecosystem for the first time.

The seven extensions this fork bundles aren't merely "supported" in the passive sense either — they're maintained in-house, shipped through the project's own manifest mirror, ported onto the new contract, and kept in lockstep with core releases instead of left to drift the way third-party plugins historically did the moment a maintainer moved on. The version bump to 17.0.0 is a one-time, deliberate break — every pre-17 plugin stops working, on purpose — specifically so that from here forward, breaks stop being routine. And the migration path for an existing install isn't a rolling in-place upgrade at all: a one-time import:legacy command moves an old install's data onto the new schema and contract once, cleanly, rather than trying to keep two incompatible worlds patched together indefinitely.

H

Security hardening

P28

P28Passkey/WebAuthn support and OIDC single sign-on, a real nonce-based Content-Security-Policy instead of an unenforced one, cross-origin isolation headers, CSP violation reporting, and the rate limiter that P11's cache pools had been sitting ready for all along.

I

Plugins & layering

P29 – P30

P29The registry machinery behind P27's contract: a real plugin and theme registry, built after actually reading roughly four hundred real plugins and a full theme library in the wild rather than guessing at what a real extension API needs — 162 distinct legacy hook names got mapped in the process, and all seven bundled extensions now run on the new contract for real.

P30The web root gets fully isolated from application code, and the repository layout itself gets the same decoupling discipline applied to the rest of the codebase — no leftover shortcuts from the migration order the earlier epochs had to take.

J

Presentation, templating & extension surface

P31 – P54

By far the longest epoch — every backend phase above had to land before any of it could start, and the frontend gets the same rigor the backend just went through.

P31Smarty, gone

All 135 templates move off Smarty and onto Latte over about eighty commits, and the point of switching engines was never syntax. Smarty let a controller reach back into template internals, and a template reach forward into the controller's — Latte's own visibility rules make that a compile error instead of a code-review convention. The old dependency, its patches, and every last template file in the old format are gone. Not deprecated. Gone.

P32Tooling nobody else had built yet

No prior art existed for either half of this phase, so both are genuinely new work rather than an off-the-shelf integration. A Piwigo-native static-analysis pipeline compiles all 135 templates with typed variable injection and analyzes the result with the same strict PHPStan configuration the rest of the codebase runs under, mapping errors back to real template lines. Alongside it, a hand-written Latte-aware code formatter — a real recursive-descent parser producing a typed syntax tree, printed through the same document-builder architecture a production-grade formatter would use — because nothing like it existed for this template language before.

P33Eight small campaigns to make Latte read like Latte

A content pass cleaning up Smarty-era patterns that survived the mechanical P31 conversion, without changing rendered output: modern whitespace and loop-scoping features turned on; type-declaration blocks generated from a live variable map instead of hand-maintained; 451 conditional and loop constructs converted to native Latte attribute syntax across 91 templates; unsafe-escape-bypass usage reduced across more than a thousand call sites, with the genuinely unsafe remainder explicitly deferred rather than silently dropped; native translation tags; locale-correct number formatting (proven, not assumed — a French locale's grouping character genuinely differs from what the old formatting call produced); and a development-only debug bar that stays off in production by default.

P34The event system gets rebuilt on a standard, PSR-14-conformant dispatcher, and the dead machinery the old bespoke dispatcher existed to support — none of which had a real caller left — gets deleted along with it. Roughly 156 event classes get pruned down to the ones with actual evidence behind them and given names that describe what they represent instead of what they used to be called.

P35A committed, explicit browser-support baseline, and everything that baseline obsoletes removed with it — IE6 PNG-alpha shims, IE7 conditional stylesheets, every `-ms-filter`/`zoom:1` fallback rule still sitting in the tree.

P36Real asset-manifest resolution through Vite replaces the roughly thousand-line hand-rolled PHP combiner from section 09 — the delivery mechanism the next several phases build on, not a content change by itself.

P37One typed payload per page, exposed as a real JSON data island, replacing dozens of ad hoc inline `json_encode()` calls smuggling PHP state into JavaScript.

P38–P39Every inline <script> and <style> block still living inside a template — including the ones hidden inside footer-captured script blocks, not just the obvious ones — moves out to real, separately loaded files.

P40One typed view per page

The largest single change in the epoch. Every template gets one real, immutable view object of its own, carrying exactly the data that template needs with a real declared type for each field — and the template's own header collapses from a large block of generated type declarations down to one line naming that class. That one change deletes all 93,420 lines of generated boilerplate that section 05's untyped variable bag had been forcing every template to carry, deletes the array-conversion method every old template-context class needed, and lets the old 1,370-line, 36-method `Template` god-class finally get split into what it always should have been: a renderer, a template locator, a theme-inheritance resolver, and a handful of other single-purpose pieces. A leftover, essentially unused "extend templates" feature — samples only, no real installs depending on it — gets deleted along with the tooling that existed only to support it.

P41Rendering flips to compose the page shell after the content instead of before it, letting the old 800-line header and 700-line footer templates finally merge into one real layout with real template inheritance. The old page-state god-object gets split by actual concern — page messages, layout chrome, debug metrics — instead of staying one 25-property grab bag.

P42One typed way for a plugin to add anything to a page

Core used to ship two different ad hoc mechanisms for the same need — one collector for admin buttons, a separate string-concatenation point for admin actions — because each need got solved locally as it came up, the same story as section 08's plugin problem playing out inside core's own code. The fix isn't a bigger version of the same idea; a survey of the plugin ecosystem found that a huge share of real customization — well over a hundred of the roughly four hundred plugins surveyed — exists purely to inject content Piwigo simply never gave a documented place to put. That demand sorts into a genuinely finite list of kinds: an admin form field, a row of picture info, a profile field, an auth button, a thumbnail overlay. Since the kinds are finite, contributions became typed value objects instead of string-keyed slots carrying raw HTML — the type determines where something renders, so there's no slot name left to typo into a silently disconnected dead end. A wrong kind is a compile-time type error. A wrong target is an invalid enum case Latte itself would reject. Both core and every theme render every contribution, so a theme can restyle what a plugin contributes rather than being stuck with whatever markup the plugin author guessed at.

P43The residual HTML-escaping cleanup, sized honestly after P40 rather than guessed at up front — the URL-and-pre-escaped-value pattern that's left once typed views have already absorbed the JavaScript-context cases P38 handled.

P44The lint and formatting tooling P32 built finally gets wired into CI and pre-commit hooks for real, rather than existing but running nowhere.

P45Every JavaScript file becomes a real TypeScript file with real types satisfying a strict compiler configuration — mechanical, same behavior, same output.

P46Typed consumption of P37's page-data payload, with TypeScript's escape-hatch `any` type driven to zero as its own tracked metric rather than left as a someday goal.

P47Monolithic per-page scripts get broken into real ES modules — shared utilities factored out, one real bundle entry per actual page rather than one enormous shared blob.

P48jQuery removed, per surface rather than all at once in a way that would have silently missed something: first-party call sites onto native DOM and fetch, the vendored library itself deleted once nothing references it anymore, UI widgets replaced or deliberately kept vendored case by case, and — the surface most likely to get missed — the installer's own separate jQuery load, checked and handled on its own.

P49A small catalog of real web components, built only for the handful of widgets P48 found no reasonable vanilla-DOM replacement for. Most of the frontend didn't need this at all.

P50An idiomatic pass over the now-modular, fully typed, jQuery-free frontend the previous six phases produced — same behavior, cleaner shape.

P51A real modern CSS architecture — container queries, cascade layers, a utility framework adopted rather than another decade of accreted overrides — with every visual output checked against the previous rendering, pixel for pixel, not just eyeballed.

P52A real modern image pipeline: AVIF and WebP variants served through the standard <picture> element, with blurred low-resolution placeholders while a full image loads instead of a blank gap.

P53Dark mode — a real theme toggle plus automatic `prefers-color-scheme` support, built on P51's cascade layers rather than a second parallel stylesheet.

P54The closing gate: real, enforced Lighthouse performance, accessibility and best-practices thresholds, and real per-bundle size budgets — both of which existed only as unenforced placeholders before this phase, collecting numbers nobody was required to act on.

13

Keeping it that way

Individual phases above mention their own piece of this in passing — P0 and P5's static analysis, P6's architecture boundary, P32's from-scratch Latte tooling, P45's TypeScript linting. Worth pulling into one picture, because none of it works as isolated tools; it works as one discipline applied consistently across three different languages.

Lint and format, three languages, one discipline

  • PHP — a style checker holding zero violations as a blocking gate, a modernization tool applying the full PHP 8.5 rule set tree-wide, and static analysis at level 10 (the strictest the tool offers) at zero errors, also blocking. A second, independent static analyzer runs alongside as a best-effort second opinion, deliberately non-blocking — two gates that both cry wolf on the same thing teach people to ignore gates, so only one gets to actually block a merge.
  • JavaScript / TypeScript — its own linter, a stylesheet linter, and dead-export detection.
  • Templates — the formatter and analysis pipeline from P32, purpose-built because nothing off the shelf existed for this template language.
  • Architecture — the six-layer boundary from Epoch B isn't a one-time migration check; it runs on every push, still at zero violations, same as the day it was introduced.

Mutation testing as the check on the checkers

All of the above proves the code is well-typed and consistently styled. None of it proves the code does the right thing. Mutation testing closes that gap by deliberately breaking the code — flipping a comparison, dropping a line, shifting a boundary by one — and failing the build if no test notices. It's the gate that caught real, previously undiagnosed bugs the rest of the tooling structurally cannot see, because they're about behavior, not shape or style — a full account of what it found is in section 16. The pitch for running it at all: a gate suite is only as good as what it actually forces someone to look at, and static types don't look at behavior.

Type coverage and CI, both blocking

A dedicated type-coverage gate keeps PHP's typed surface from eroding one untyped parameter at a time instead of trusting that it won't; TypeScript's any escape hatch is tracked down to zero the same way. All of it runs across 34 CI jobs on every push, including a genuine three-way database matrix — MySQL, MariaDB and PostgreSQL, not just "works on my machine's database" — plus dependency and supply-chain scanning and a lint pass over the CI configuration itself. The rule that makes all of it mean something: nothing lands unless CI is green on a clean checkout. CI, not a local machine, is the source of truth for "passing."

16

What broke, and got caught

The gates in section 13 aren't decorative, and the honest way to show that is with what they actually found — real defects, caught and fixed during the work, that a reviewer reading the same code by eye had already missed.

  • A bound-parameter sweep across the codebase turned up several real, live SQL injection vulnerabilities beyond the WS layer's own — three in the image repository, one in comments, one spanning history and notifications, and a plugin-hook injection point, all fixed as part of moving every raw SQL splice onto bound parameters.
  • A config-synchronization bug where a value written to the database never actually reached the live, in-memory config object that security-sensitive code read from — the concrete symptom was a CSRF service silently operating with an empty secret key.
  • A distributed-lock naming scheme was using a hash of the (now-removed) table-prefix setting as its uniqueness entropy — silently unsafe on any shared database server, fixed by keying on the database name instead, which is actually guaranteed unique per install.
  • The architecture-boundary checker itself had a real bug — a hyphen in a layer name silently broke its rule resolution, misreporting every legal cross-layer dependency as a violation. Worth remembering: when a tool's output looks structurally wrong, suspect the tool before you suspect the code.
  • Mutation testing surfaced four bugs nothing else caught: a maintenance job reading the real wall clock instead of the injectable one tests can freeze; a URL builder appending a stray trailing colon nobody had ever noticed because nothing rendered it visibly; a French pluralization file with a corrupted accented character sitting inside a regular expression; and a leaked process file-creation mask in the upload handler.
17

Where it stands

Fifty-five phases, ten epochs, a codebase that went from no automated tests and thirty-four MyISAM tables to a fully typed, layer-enforced, worker-mode-ready application without losing a photo along the way. The parts I'd point to if someone asked what actually mattered, rather than what was merely satisfying to delete: giving every unit of state an actual owner, giving every plugin a real contract instead of undocumented internals to guess at, and giving translators a format a normal tool understands instead of a PHP file only a developer could safely touch. None of those are glamorous. All three were load-bearing.

Twenty-three years from now, someone else can tell me whether any of this held up. For now: the architecture checker passes, the strictest static-analysis level the tooling offers passes at zero errors, and the photos still load.
