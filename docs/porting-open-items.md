### Framework-level gaps (block any future plugin, not just the 2 above)

- [x] ~~No general raw-DB read/write surface.~~ — **done 2026-09-13**: `ExtensionContext::db(): ExtensionDatabase` (`src/Piwigo/PluginConfig/ExtensionDatabase.php`), for the real fraction of the 170/406+97/406 `pwg_query()` callers that genuinely need their own custom table (traced to `BanIP_13.0.a`'s row-addressable `ip_ban` table and `AdditionalPages_14.a`'s `CREATE TABLE IF NOT EXISTS`) — not a raw `Connection` passthrough: `tableName(string $suffix)`/`hasTable()`/`createTable()`/`dropTable()`/`insert()`/`update()`/`delete()`/`select()`/`count()`, every method resolving the table internally to `ext_<extensionId>_<suffix>` so an extension is structurally unable to name any table but its own (no method anywhere accepts a table name or raw `FROM`/`JOIN` target from the caller). `update()`/`delete()`/`select()`/`count()` take a `Piwigo\Permission\SqlCondition` (already this codebase's own parameterized-WHERE-fragment primitive) rather than a raw SQL string, for real expressiveness (BanIP's own `LIKE` range match) without reopening a way to reference a second table. `createTable()`'s DDL goes through `Doctrine\DBAL\Schema\Table`/`AbstractSchemaManager` (portable across MySQL/Postgres/SQLite from one column description) rather than hand-written per-platform SQL, deliberately not requiring of plugin authors the same 3-dialect-by-hand discipline this fork's own `Piwigo\Migrations\Version*` classes need for core's schema — that would have been a real regression risk to this fork's completed Postgres-portability work. Two real bugs found and fixed via an actual hyphenated-extension-id test (not just design review): neither `createTable()` nor `dropTable()` auto-quotes an identifier needing it (`PluginId`/`ThemeId` both allow hyphens) — both now go through a `quotedTableName()` helper; `hasTable()`'s `tablesExist()` is the one exception that's genuinely safe unquoted (schema introspection, not raw SQL text). **Boundary decided during design, not left implicit**: `db()` is for unbounded/row-queryable data only — small, fixed-shape state stays on `getSetting()`/`setSetting()` (a first pass wrongly called `BanIP`'s own IP-ban list "small," when its real admin UI does individual per-row edit/delete/range-match, squarely a `db()` case).

Turned out to be about closing a real, live piece of duplication in core itself, not just adding plugin surface: `$_SESSION['page_infos']`/`$_SESSION['page_errors']` are core's own current flash-message mechanism (read back by `Html\HtmlService::flushMessageList()` on the next request, needed because `PageState::addInfo()`'s in-memory accumulation can't survive a redirect), written raw and duplicated across 11 real call sites in 8 files (`CommentsController`, `PictureController`, `RegisterController`, `PasswordController`, `BatchManagerGlobalPageRenderer`, `BatchManagerSubController`, `CatListPageRenderer`, `MaintenanceActionDispatcher`). - [x] ~~No request/query-parameter accessor reachable from `boot()` or an early-firing event.~~ — **done 2026-09-13**: `ExtensionContext::queryParam()`/`postParam()`. Turned out the "reachable from `boot()` *or* an early-firing event" framing in the original item text was a red herring: `$_GET`/`$_POST` are populated by PHP before any user code runs at all, so there's no actual timing constraint the way there is for `template()`/`currentUser()` — the only real gap was that `ExtensionContext` had no accessor for them at any point. Deliberately 2 explicit methods, not one `$_REQUEST`-reading method: `$_REQUEST`'s composition depends on the `request_order` php.ini directive (and historically could include `$_COOKIE`), which this fork can't guarantee across every deployment — `queryParam()`/`postParam()` matches how every other core `*Request` VO takes `$_GET`/`$_POST` as two separate arrays rather than one merged one; `CsrfTokenRequest`'s own existing `$_REQUEST` read is fine as a narrow one-off internal token check, not as a new unbounded-caller framework contract. No per-extension namespacing (unlike `session()`/`cookies()`/`db()`): a request is the caller's own, already fully controlled by whatever URL its own templates/links generate, so there's no cross-extension collision for the framework to guard against. String-only, absent/non-string/empty-string collapsing to `null`, matching `CsrfTokenRequest`'s own established convention — checked the plugin corpus for a real array-shaped `$_GET`/`$_POST` need at boot-relevant call sites and found none.
- [x] ~~No `ExtensionContext` accessor for "is another named extension active" — `PluginRegistry::isActive(string $pluginId): bool` exists but isn't reachable from `ExtensionContext` at all.~~ — **done 2026-09-13**: `ExtensionContext::isPluginActive()`. Grounded in a real, recurring legacy idiom, not just `block_search_13.0.a`'s own `SELECT state FROM PLUGINS_TABLE WHERE id = 'PWG_Stuffs'` check: `most_downloaded_12.0.a` and `whois_online_menu_12.0.a` both gate their own registration on the exact same "is this specific sibling plugin active" check against a different plugin id. Deliberately doesn't inject `PluginRegistry` itself (the first, naive shape): `PluginRegistry`'s own constructor already depends on `ExtensionContextFactory` (to build the context it hands each plugin's `boot()`), so that would be a real circular dependency, not just a style choice. `PluginRegistry::isActive()` is itself just `$this->repository->getDbPlugins('active', $pluginId) !== []`, reached instead the same way `db()` already reaches `Connection` — via the already-injected `EntityManagerInterface`, with zero new constructor dependencies added anywhere (`PluginEntity`'s own `repositoryClass` mapping makes `TypedRepository::narrow()` a zero-cost assert here, not a real cast, matching `MaintenanceActionDispatcher`'s own identical pattern for `SiteRepository`). Deliberately plugin-only (raw `string`, not `PluginId|ThemeId`): checked the theme corpus too, found zero equivalent "is another theme active" callers.

A webmaster *can* already reach code execution today via the real, existing plugin-install-from-zip feature (`Admin\PluginsNewPageRenderer`/`ZipExtractor`), so this isn't about making code execution possible that wasn't — it's that a bare `$_POST['submit']` + textarea is a dramatically lower-friction, less auditable primitive for a CSRF/session-hijack attacker than crafting and installing a whole plugin zip. Porting this tab would hand back exactly the shortcut `DeploymentPolicy` was built to remove.
  - **`tpl`** (creates/edits arbitrary `.tpl` files under `./template-extension/`) — structurally gone: grepped the whole v17 tree for `template-extension`, zero hits. - [x] ~~Config-value migration format for a real 16.x→17.x upgrade — thought to be a `ConfigService` fallback gap.~~ — **reframed 2026-09-13, not a `ConfigService` fix at all.** Checked the real schema first: `config.value` is a native `json`/`jsonb`-*typed* column (`Migrations/Version20260804122302.php`), not a `varchar` treated as JSON by convention — the database itself rejects a raw legacy PHP `serialize()`d string (`a:2:{...}`) on write, so this can't manifest as `ConfigService::confGetParam()` silently returning defaults at read time the way the original item assumed; it would fail earlier, at whatever step tries to get a legacy row into this table at all. Checked what that step even is: `docs/REFERENCE.md`'s own "Key design decisions" states plainly — **"Clean fork, no in-place upgrade from upstream Piwigo. Existing installs adopt v17 via a one-time `bin/piwigo import:legacy` migration (not built yet)."** There is no 16.x→17.x data-import tool anywhere in this fork yet. Writing a `ConfigService` legacy-format fallback today would fix the wrong layer for a caller that doesn't exist, with no visibility into how that future tool will actually decode each legacy config key (serialize()/JSON/plain-scalar format varies per key in real legacy Piwigo, not uniform). Correctly belongs as a design requirement for `import:legacy`'s own per-key decode step, not a standalone fix — recorded here as that requirement, not as an open framework gap to act on now. Real precedent for how this fork actually repairs bad `config.value` rows when it does act: `Migrations/Version20260828120000.php` (P58-A), a dedicated Doctrine migration, not a `ConfigService` runtime fallback.
