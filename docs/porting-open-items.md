### Framework-level gaps (block any future plugin, not just the 2 above)

- [x] ~~No general raw-DB read/write surface.~~ — **done 2026-09-13**: `ExtensionContext::db(): ExtensionDatabase` (`src/Piwigo/PluginConfig/ExtensionDatabase.php`), for the real fraction of the 170/406+97/406 `pwg_query()` callers that genuinely need their own custom table (traced to `BanIP_13.0.a`'s row-addressable `ip_ban` table and `AdditionalPages_14.a`'s `CREATE TABLE IF NOT EXISTS`) — not a raw `Connection` passthrough: `tableName(string $suffix)`/`hasTable()`/`createTable()`/`dropTable()`/`insert()`/`update()`/`delete()`/`select()`/`count()`, every method resolving the table internally to `ext_<extensionId>_<suffix>` so an extension is structurally unable to name any table but its own (no method anywhere accepts a table name or raw `FROM`/`JOIN` target from the caller). `update()`/`delete()`/`select()`/`count()` take a `Piwigo\Permission\SqlCondition` (already this codebase's own parameterized-WHERE-fragment primitive) rather than a raw SQL string, for real expressiveness (BanIP's own `LIKE` range match) without reopening a way to reference a second table. `createTable()`'s DDL goes through `Doctrine\DBAL\Schema\Table`/`AbstractSchemaManager` (portable across MySQL/Postgres/SQLite from one column description) rather than hand-written per-platform SQL, deliberately not requiring of plugin authors the same 3-dialect-by-hand discipline this fork's own `Piwigo\Migrations\Version*` classes need for core's schema — that would have been a real regression risk to this fork's completed Postgres-portability work. Two real bugs found and fixed via an actual hyphenated-extension-id test (not just design review): neither `createTable()` nor `dropTable()` auto-quotes an identifier needing it (`PluginId`/`ThemeId` both allow hyphens) — both now go through a `quotedTableName()` helper; `hasTable()`'s `tablesExist()` is the one exception that's genuinely safe unquoted (schema introspection, not raw SQL text). **Boundary decided during design, not left implicit**: `db()` is for unbounded/row-queryable data only — small, fixed-shape state stays on `getSetting()`/`setSetting()` (a first pass wrongly called `BanIP`'s own IP-ban list "small," when its real admin UI does individual per-row edit/delete/range-match, squarely a `db()` case).
- [x] ~~No Smarty compile-time-hook equivalent (`set_prefilter()`/`set_extents()`)~~ — **resolved 2026-09-13, reframed: no generic compile hook needed at all.** All 8 named plugins use `set_prefilter()` only (none actually use `set_extents()`); read every one's real callback and cross-checked against this fork's own already-established replacement mechanism — 11+ typed "named contribution" classes (`ThumbnailOverlay`, `PictureInfoRow`, `ButtonContribution`, `ActionContribution`, `FieldOverride`, `ProfileField`, `FormProvider`, `AssetContribution`, ...), each with a docblock naming the exact legacy prefilter plugin it replaces. Per plugin:
  - `custom_download_link_14.a`, `download_formats_buttons_16.a` — **already solved**, `ButtonContribution`/`ActionContribution` (picture-page action buttons).
  - `de_activate_all_languages_13.0.a` — **already solved**, its whole prefilter is pure JS/CSS injection (`combine_script`/`combine_css`), covered by `AssetContribution`/`GetPageAssets` with no template targeting needed at all.
  - `NoPassword` — **already solved**, both halves: `profile_content` maps to `FieldOverride::Password` (its own docblock already names this exact need, via the equivalent `oAuth` plugin); `user_list` is pure asset injection, `AssetContribution` again.
  - `hide_title_on_browse_path_12.a` — **verified needs no core change**: its target, `.browsePathSeparator` (+ the following `<h2>`), still exists unchanged in `picture.latte` and has zero competing CSS rule anywhere in this fork — a plugin's own contributed CSS achieves this with nothing to fight in the cascade.
  - `pAnchor_0.5b` — **verified needs no core change**: its anchor point, `<div id="imageHeaderBar">`, still exists at the same position in `picture.latte`; since HTML `id` attributes have been valid URL-fragment jump targets since forever (unlike the `<a name>` convention the plugin was built around), the whole "jump to photo, not page-top" feature works today via a plain `#imageHeaderBar` suffix on nav links — checked `PictureController` too, confirming no event wraps next/prev URL construction, so this is a client-side-only need, not a missing hook.
  - `edit_filename_12.a` — **the one real, done gap**: submit-side rename logic already maps onto the existing (previously unused) `Piwigo\Admin\Event\PictureModifyBeforeUpdate` typed event, matching legacy's `picture_modify_before_update` 1:1. The missing render-side half — no way to add a field to the admin picture-edit form — is now closed: new `Piwigo\Contribution\PictureEditField` (mirrors `ProfileField`), `Template::addPictureEditField()`/`pictureEditFields()`, wired through `PictureModifyView::$pluginPictureEditFields` and rendered in `picture_modify.latte` right before the Title field (legacy's own exact anchor).
  - `tag_groups_14.f` — **not a hook problem, a standalone feature-design gap**: decomposes into a tag-naming convention (pure data logic), a genuinely alternate "browse by group" display mode (a closed, typed `TagsView::$displayMode` concept, not a pluggable extension point — adding a 3rd mode is a real core change of its own), and one index-page widget-injection need (fits the established contribution-class pattern, but needs its own new class when actually prioritized). Its own literal `tg_add_display_link_prefilter` regex anchors are already stale against the current `tags.latte` (the `{if $display_mode == 'letters'}`-style Smarty conditionals it targets don't exist anymore — replaced by a typed `n:if="$displayMode === 'letters'"`), so it couldn't be ported verbatim regardless of what hook mechanism existed. Left as its own future design item, not folded into this one.
- [x] ~~No `ExtensionContext` accessor for a *shared* core session key beyond the 3 already covered (`coreIndexDeriv()`/`corePictureDeriv()`/`isShowMetadataEnabled()`). Real example: `bot_protection/admin/bot_protection_admin.php` writes into `$_SESSION['page_infos']`, a shared core key with no named accessor.~~ — **done 2026-09-13**: `ExtensionContext::addPageInfo()`/`addPageError()`, backed by new `SessionService::queuePageInfo()`/`queuePageError()`. Turned out to be about closing a real, live piece of duplication in core itself, not just adding plugin surface: `$_SESSION['page_infos']`/`$_SESSION['page_errors']` are core's own current flash-message mechanism (read back by `Html\HtmlService::flushMessageList()` on the next request, needed because `PageState::addInfo()`'s in-memory accumulation can't survive a redirect), written raw and duplicated across 11 real call sites in 8 files (`CommentsController`, `PictureController`, `RegisterController`, `PasswordController`, `BatchManagerGlobalPageRenderer`, `BatchManagerSubController`, `CatListPageRenderer`, `MaintenanceActionDispatcher`). Found a real, live bug while reading every call site rather than assuming they were all identical: 6 of them did `$_SESSION['page_infos'] = [$message]` (direct overwrite) instead of appending, silently discarding anything queued earlier in the same request — a landmine the new plugin-facing accessor would have walked straight into. All 11 sites refactored to the new shared, append-only methods, fixing the clobbering bug as part of the same change (not left as a separate item), mutation-verified against the old overwrite behavior via `MaintenanceActionDispatcherTest`. Deliberately only 2 methods, not 4: `page_warnings`/`page_messages` have zero real raw-session callers anywhere in this codebase, so `queuePageWarning()`/`queuePageMessage()` would have been ungrounded speculative surface. `string`-only (not `string|Html` like `PageState::addInfo()`): confirmed live that `flushMessageList()`'s own read side silently drops non-string values from the session array, so an `Html` value queued here would just vanish on the next request.
- [x] ~~No request/query-parameter accessor reachable from `boot()` or an early-firing event.~~ — **done 2026-09-13**: `ExtensionContext::queryParam()`/`postParam()`. Grounded in `TakeATour_16.3.0/main.inc.php`'s own real top-level `isset($_REQUEST['submited_tour_path'])`/`isset($_GET['tour_ended'])`/`$_GET['page'] == "plugin-TakeATour"` reads (already a named bundled target on this list) — these decide whether the plugin even registers an `init` handler, and `Preload/main.inc.php` gates its own `add_event_handler()` call the same way on `isset($_GET['slideshow'])`. Turned out the "reachable from `boot()` *or* an early-firing event" framing in the original item text was a red herring: `$_GET`/`$_POST` are populated by PHP before any user code runs at all, so there's no actual timing constraint the way there is for `template()`/`currentUser()` — the only real gap was that `ExtensionContext` had no accessor for them at any point. Deliberately 2 explicit methods, not one `$_REQUEST`-reading method: `$_REQUEST`'s composition depends on the `request_order` php.ini directive (and historically could include `$_COOKIE`), which this fork can't guarantee across every deployment — `queryParam()`/`postParam()` matches how every other core `*Request` VO takes `$_GET`/`$_POST` as two separate arrays rather than one merged one; `CsrfTokenRequest`'s own existing `$_REQUEST` read is fine as a narrow one-off internal token check, not as a new unbounded-caller framework contract. No per-extension namespacing (unlike `session()`/`cookies()`/`db()`): a request is the caller's own, already fully controlled by whatever URL its own templates/links generate, so there's no cross-extension collision for the framework to guard against. String-only, absent/non-string/empty-string collapsing to `null`, matching `CsrfTokenRequest`'s own established convention — checked the plugin corpus for a real array-shaped `$_GET`/`$_POST` need at boot-relevant call sites and found none.
- [x] ~~No `ExtensionContext` accessor for "is another named extension active" — `PluginRegistry::isActive(string $pluginId): bool` exists but isn't reachable from `ExtensionContext` at all.~~ — **done 2026-09-13**: `ExtensionContext::isPluginActive()`. Grounded in a real, recurring legacy idiom, not just `block_search_13.0.a`'s own `SELECT state FROM PLUGINS_TABLE WHERE id = 'PWG_Stuffs'` check: `most_downloaded_12.0.a` and `whois_online_menu_12.0.a` both gate their own registration on the exact same "is this specific sibling plugin active" check against a different plugin id. Deliberately doesn't inject `PluginRegistry` itself (the first, naive shape): `PluginRegistry`'s own constructor already depends on `ExtensionContextFactory` (to build the context it hands each plugin's `boot()`), so that would be a real circular dependency, not just a style choice. `PluginRegistry::isActive()` is itself just `$this->repository->getDbPlugins('active', $pluginId) !== []`, reached instead the same way `db()` already reaches `Connection` — via the already-injected `EntityManagerInterface`, with zero new constructor dependencies added anywhere (`PluginEntity`'s own `repositoryClass` mapping makes `TypedRepository::narrow()` a zero-cost assert here, not a real cast, matching `MaintenanceActionDispatcher`'s own identical pattern for `SiteRepository`). Deliberately plugin-only (raw `string`, not `PluginId|ThemeId`): checked the theme corpus too, found zero equivalent "is another theme active" callers.
